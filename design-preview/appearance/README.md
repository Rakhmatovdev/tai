# Brave appearance refinement

The ordinary graphite/copper interface remains the default. The optional Hacker theme uses a restrained green accent, layered green-black surfaces, a clipped grid, corner brackets and the existing voice-reactive portrait in wireframe. Text stays in Segoe UI for readability; instrument labels use Consolas. All graphics are local Qt/vector rendering; no remote fonts, bitmap downloads or new dependencies are required.

The gear opens one searchable Settings window with six sections. Appearance, language, profile and audio forms are embedded in it; plugin and remote tools retain their specialized panels. The appearance page shows all three themes side by side and marks the active selection. Choice is saved immediately. Returning to Default or Light restores the user's saved accent. An unsaved profile accent preview is reverted on close. Memory is managed in Center, and chat export lives in the chat overflow menu.

Ctrl+K opens a separate compact command search without adding a main-window button. Settings and action metadata come from `brave_navigation.py`. Queries also search local conversation titles and bodies; a chat result opens a preview and requires an explicit Continue to resume. Queries never invoke actions. Keyboard and mouse activation check current action availability, and pending queries are flushed before Enter to avoid running a stale result. Cyrillic and Latin history searches use Unicode case folding while retaining literal wildcard escaping.

The existing chat expand button now toggles full focus: statistics, portrait, header and footer are hidden while the chat remains. Ctrl+Shift+F and quick search provide keyboard access. `brave_layout.py` stores debounced window geometry, maximized state and focus preference through the atomic local workspace store; drafts and messages are not part of this record. Saved rectangles are validated and moved into the available work areas after monitor changes. Settings → System → Layout provides remembrance opt-out and reset.

## Research

All six subsequent local conversation features are implemented: editable/pinned local memory, explicit model pull/resume, last-message edits and regeneration into preserved-history branches, lexical PDF/DOCX/text retrieval with persisted source previews, managed provider switching without restart, and opt-in Windows offline voice. `docs/LOCAL_FEATURES.md` records entry points and limits. New dialogs are previewed in all three themes and languages. Factory failures, stale backend callbacks, cancelled speech, branch source copies and provider changes during queued regeneration have dedicated checks.

A real `llama3.2:latest` check summarized older turns (14 messages covered), answered a temporary project document question with HORIZON / 42 and emitted source links. The local multilingual base speech model was prepared and its path saved only because no previous speech-model path existed. Windows SAPI synthesized an English test WAV and faster-whisper transcribed it correctly. There was no real microphone recording or live Gemini request. Installed system voices were English and Russian; Uzbek recognition/voice quality was not benchmarked. These are functional checks, not performance benchmarks.

Automatic startup and memory budgets are configured in the existing AI model page. The service manager reuses healthy servers and launches the installed CLI once on IPv4 loopback when necessary, with a process-local cloud-disable setting. Auto budgets sample available RAM / optional NVML VRAM off the GUI thread, select conservative Economy/Balanced limits, and retain manual choices. On 2026-10-16 a real service startup completed successfully; a subsequent native Qt request to `llama3.2:latest` using the automatically resolved Balanced budget returned `AUTO_LOCAL_OK` in about 5 seconds. This is a smoke result, not a performance comparison. Service lifecycle, concurrency, cancellation, persistence, resource thresholds, recovery cooldown and UI behavior are covered by `tests/test_ollama_automatic.py` and `tests/test_ollama.py`.

Verification now contains 143 checks, all passed in one full run on 2026-10-16. The settings render uses a fixed test memory snapshot and model inventory. All runtime preference writes in tests go to temporary files.

Model capability discovery and request measurements now share validated metadata in `core/ollama_model.py`. Both transports reject explicitly incompatible chat models and cap context at the model's advertised maximum. Thinking preferences are sent only when advertised as supported; missing controls on older servers use the model default. Settings shows the model's capabilities and only displays a thinking control when usable. Thinking stream activity resets the idle timer without displaying or retaining reasoning. Optional version/running-model probes cannot bypass the overall deadline. Length-limited replies include a continuation notice.

Existing Diagnostics now shows volatile metadata for the latest local request: status, requested model/profile, server version, context, initial residency, preparation/first-visible-answer/total time, model-load time and token counts/rate. No prompt, answer, reasoning or API key is retained in this metadata. `brave-local-diagnostics-{theme}-{language}.png` and refreshed Ollama settings images cover three themes and languages. The diagnostics scroll content uses the active theme surfaces.

A real native Qt smoke against Ollama 0.33.2 and `llama3.2:latest` returned `LOCAL_METRICS_OK` twice. The first request reported the model not loaded, first answer at 3.70 seconds, load time 3.25 seconds; the subsequent loaded-model request reported first answer at 0.73 seconds and load time 0.01 seconds. Each generated five tokens. These are functional checks of the metadata and timing paths, not a controlled performance benchmark or an optimization speedup claim. No model download, user preference changes or cloud inference were performed for these checks.

The model picker now loads installed names automatically, supports native completion/search, preserves unsaved selections while refreshing, and displays local model metadata. Model tags and runtime model names are treated as literal values during interface translation. Chat transport is `brave_ollama_request.py`, using built-in QtNetwork with manual redirects, no proxy, bounded timers and immediate socket abort. Existing task labels display stages inferred from [Ollama running models](https://docs.ollama.com/api/ps), followed by streamed text. Tests cover cancellation before headers/during metadata/during text, old-reply isolation, timeouts, model changes on the next request, and stale inventory results after an address change. No new dependencies or header controls were added.

On 2026-10-16 the full suite passed 82 checks. Theme/language screenshots use a controlled local test inventory. A native Qt smoke attempt against localhost:11434 reached the connection-error path because the real Ollama service was unreachable; positive native streaming and cancellation were verified against local HTTP fixtures. The real-model result below belongs to the earlier synchronous client smoke test on 2026-10-15.

Offline model controls are in Settings → AI model. `brave-ollama-{theme}-{language}.png` shows the native provider/model/profile form in all three themes and languages. Local-only protocol, streaming/persistence, cancellation, first-run setup, provider startup routing, diagnostics without cloud/audio probes, and model/profile settings are covered in `tests/test_ollama.py`. The local client follows the official [chat API](https://docs.ollama.com/api/chat) and [model retention behavior](https://docs.ollama.com/faq#how-do-i-keep-a-model-loaded-in-memory-or-make-it-unload-immediately). A separate real loopback smoke test against the installed `llama3.2:latest` returned `LOCAL_OK`; its cold request took about 52 seconds on this machine, so the implementation makes no latency improvement claim. Model installation and internet disconnection were not part of that smoke test.

- [Geist colors](https://vercel.com/geist/colors): separate surface, border and text roles; use accent colour deliberately.
- [Carbon themes](https://www.carbondesignsystem.com/building-blocks/foundations/themes/overview): keep theme values behind semantic tokens so a theme applies throughout the interface.
- [Vercel interface guidelines](https://vercel.com/design/guidelines): visible keyboard focus, descriptive accessible names and legible numerical information.

These principles were adapted to native PyQt6 widgets. No external component code was copied.

## Verification

Latest follow-up implementation: **164 tests passed**. New dialogs were rendered in dark/light/hacker × UZ/EN/RU. Synthetic 10,000-message paging, native embedding cancellation, source-backed facts/branches, model comparison, backup/restore and isolated installer update/rollback are covered. The frozen executable opened the main window and three new dialogs on this Windows host. Real Ollama and OCR evidence is in `local-real-smoke.json`; a repeated comparison is in `real-model-comparison.json`. See `../../docs/NEXT_LOCAL_FEATURES.md` for limitations. This is not a clean-VM certification or an overall Uzbek quality benchmark.

`tests/test_appearance.py` checks theme persistence, draft preservation, palette round trips, focus styling, text contrast, settings search, embedded forms, local history search, keyboard shortcuts, busy guards, pending-query activation, focus transitions, layout restart restoration, debounce, opt-out, reset and invalid/offscreen geometry. Rendering covers three languages, three themes and two main-window sizes, including settings, quick search and full focus. Body, secondary and muted text are checked against the three main surfaces at a minimum contrast ratio of 4.5:1. This is a targeted check, not a complete accessibility audit.

Run from the project directory in PowerShell:

```powershell
$env:BRAVE_UI_PREVIEWS = 'design-preview/appearance'
.venv/Scripts/python.exe -m unittest discover -s tests -v
```
